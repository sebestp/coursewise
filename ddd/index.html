一、贫血模型的问题 · 1.1

什么是贫血模型

贫血模型（Anemic Domain Model）：领域对象只有字段 + getter/setter，没有行为。

public class Order { private String orderId; private String status; private BigDecimal totalAmount; private Date paidAt; // 全是 getter / setter，没有业务方法 public void setStatus(String status) { this.status = status; } public void setPaidAt(Date paidAt) { this.paidAt = paidAt; } // 谁都能调 }
  • •最典型的例子就是订单 Order——有订单 ID、状态、金额、支付时间等字段，但业务方法不在 Order 里。
    • 一、贫血模型的问题 · 1.2

    后果：规则外流，Service 变胖

    // OrderService.pay() public void pay(String orderId) { Order o = dao.select(orderId); if ("PAID".equals(o.getStatus())) throw ...; // 规则流到这里 if ("CANCELLED".equals(o.getStatus())) throw ...; o.setStatus("PAID"); // 对象自己管不住状态 o.setPaidAt(new Date()); dao.update(o); pointsService.add(o.getCustomerId(), o.getAmount()); // 依赖越滚越多 smsService.send(o.getPhone(), "支付成功"); }
  • •Order 没有行为 → 规则只能外流 → Service 被迫变胖，一个方法里塞进越来越多的依赖。
    • 一、贫血模型的问题 · 1.3

    贫血模型的三个问题

  • 1违背面向对象：对象应封装数据 + 行为，贫血模型把它们分开了，对象是「苍白」的。
  • 2Service 变胖：业务复杂后，一个 Service 几千上万行，所有订单代码堆在一起，无法再拆分。
  • 3违反开闭原则：每次改动都要打开 Service 添砖加瓦，久而久之不可维护。
    • 二、DDD 的解决思路 · 2.1

    贫血写法 vs DDD 的主张

    传统贫血写法DDD 的主张
    以数据表为中心建对象以 业务不变量 为中心建聚合
    order.setStatus("PAID")order.pay() —— 对象自己拒绝非法流转
    一个 Service 管多个对象一个事务只改一个聚合
    上层依赖下层的具体实现依赖倒置：内层定义接口，外层实现
    一个系统一套模型按限界上下文切分模型
    二、DDD 的解决思路 · 2.2

    demo 里的两条边界（限界上下文）

    com.shop.order 订单上下文 ← 主线 com.shop.product 商品上下文 ← 协作方
  • •同一个「商品」：订单只要快照（ID、名称、当时价格），商品才是完整聚合（价格、库存、状态）。

    三、DDD 分层 · 3.2

    依赖规则与「插座」比喻

  • •箭头指向 domain：domain 不认识任何框架、数据库、外部服务。
  • •与三层架构对比：三层按技术拆分（表示/业务/数据），DDD 按业务拆分。
  • •接口位置颠倒：三层里业务层依赖数据层的 DAO 接口；DDD 里接口定义在 domain（由使用者定义），infrastructure 实现它。

    • 🔌 插座比喻

    教室墙上的 220V 插座，是教室根据教学需要定义的接口，不是电网决定的。车间要三相电，就定义三相接口——「我需要什么接口，就装什么接口，供电方来实现」。

    目录结构：按上下文分包，每层一包

    四、目录结构 · 4.2

    目录背后的规则

    规则理由
    domain 零 Spring / JPA 注解领域可 new 出来直接测，不依赖容器
    仓储接口在 domain，实现在 infrastructure换数据库不动业务代码（DIP）
    对外只返回 DTO（OrderView）外部拿不到聚合，绕不过 pay() 乱改状态
    一个 @Transactional 只改一个聚合事务边界 = 一致性边界
  • ✓验证方法：把 Spring 从 classpath 拿掉，domain 包还能编译，才算划对了。
    • 五、用户接口层 · 5.1

    Controller 只做翻译和转发

    @RestController @RequestMapping("/api/orders") public class OrderController { private final OrderApplicationService applicationService; // 只依赖应用服务 @PostMapping @ResponseStatus(HttpStatus.CREATED) public OrderView place(@Valid @RequestBody PlaceOrderCommand cmd) { return applicationService.placeOrder(cmd); // 一行 } @PostMapping("/{orderId}/pay") public OrderView pay(@PathVariable String orderId) { return applicationService.payOrder(orderId); // 一行 } }
  • •入参 PlaceOrderCommand、出参 OrderView 都是 DTO，不是聚合。
  • •领域异常在这里翻译成 HTTP 状态：OrderStateException → 409 Conflict。
    • 六、应用服务层 · 6.1

    应用服务 = 一个用例的编排脚本

    @Transactional public OrderView placeOrder(PlaceOrderCommand cmd) { // 1. 查外部依赖（商品快照 + 会员等级） List<...> snapshots = cmd.items().stream() .map(line -> productPort.getProduct(line.productId()) .orElseThrow(() -> new IllegalArgumentException("商品不存在"))) .toList(); MemberLevel level = memberLevelPort.getLevel(cmd.customerId()); // 2. 委托给领域（校验 + 定价 + 事件都在里面） Order order = Order.place(..., new Address(...), level, pricingService); // 3. 保存 → 发事件 → 转 DTO orderRepository.save(order); eventPublisher.publish(order.pullEvents()); return OrderViewAssembler.toView(order); }

    固定套路

    查依赖 → 调聚合 → 存 → 发事件 → 转 DTO

    六、应用服务层 · 6.2

    应用服务的边界

    不做什么谁来做
    不写业务 if / switch聚合 Order.pay()
    不算金额领域服务 OrderPricingService
    不碰 JPA / SQL仓储 OrderRepository
  • •@Transactional 画出的就是一致性边界：一个事务只改一个聚合。硬性约束：应用服务里找不到任何基于 OrderStatus 的 if/switch。
    • 七、领域层：核心构件 · 7.1

    domain 包里有什么

    com.shop.order.domain/ ├── Order.java 聚合根 ├── OrderItem.java 实体 ├── OrderId / Money / Address 值对象 ├── OrderPricingService.java 领域服务 ├── OrderPlacedEvent / Paid / Cancelled 领域事件 ├── OrderRepository.java 仓储接口 └── ProductPort / MemberLevelPort.java 端口
    七、领域层 · 7.2

    聚合根 Order：规则的守护者

    public class Order { private final OrderId orderId; // 聚合根身份 private final String customerId; // 只存 ID，不跨聚合引用 private final List<OrderItem> items; // 订单项，只读暴露 private final Address address; // 值对象 private final Money totalAmount; // 最终应付 private OrderStatus status; // 唯一可变状态 private final List<Object> domainEvents; // 内部事件列表 }
  • •一致性边界：外部只能通过聚合根访问内部，OrderItem 生命周期从属订单。
  • •越界的后果：直接从数据库取 orderItem 建对象，绕过订单业务规则（金额、库存判断）→ 订单处理失调。
  • •构造器私有 + reconstruct：外面 new 不出来，靠 place 工厂方法创建；reconstruct 供仓储从 PO 还原（绕过校验，数据已合法）。
    • 七、领域层 · 7.3

    聚合的两处入口：工厂方法与业务方法

    私有构造器为什么 place 能 new？place 在 Order 内部，内部方法可访问私有构造器；外部只能靠 place 工厂方法下订单，不能凭空 new 一张空订单。

    // 创建：工厂保证"生下来就合法" public static Order place(...) { if (snapshots.isEmpty()) throw new IllegalArgumentException("至少选择一件商品"); Money total = /* 订单项小计累加 */; Money finalTotal = pricing.apply(total, memberLevel); Order order = new Order(OrderId.newOne(), ..., finalTotal, PENDING_PAYMENT, now()); order.domainEvents.add(new OrderPlacedEvent(...)); return order; } // 变更：业务方法，没有 setter public void pay() { switch (this.status) { case PENDING_PAYMENT -> { this.status = PAID; this.paidAt = now(); this.domainEvents.add(new OrderPaidEvent(...)); } case PAID -> throw OrderStateException.cannotPayBecauseAlreadyPaid(); case CANCELLED -> throw OrderStateException.cannotPayBecauseCancelled(); } }
    七、领域层 · 7.4

    领域服务：规则不属于任何单个对象时

    需求：「会员折扣 + 满 300 减 30，不叠加」。放哪里？

    放在哪为什么不行
    Order 实体涉及会员等级与促销协作，放进去让 Order 变上帝对象
    应用服务应用服务不许写业务判断
    领域服务 ✅是业务规则，又无状态、可复用、好测试
    public Money apply(Money originalTotal, MemberLevel memberLevel) { Money afterMemberDiscount = originalTotal.discount(memberLevel.discountRate()); if (memberLevel == MemberLevel.NORMAL && originalTotal.isGreaterThanOrEqual(THRESHOLD_300)) return originalTotal.subtract(REDUCTION_30); return afterMemberDiscount; // 二选一，不叠加 }
    七、领域层 · 7.5

    领域事件与仓储接口

    📢 领域事件：记录「已发生的事实」

    OrderPlacedEvent（下单）、OrderPaidEvent（支付）、OrderCancelledEvent（取消）。和业务状态变更写在同一处。

    public List<Object> pullEvents() { List<Object> snapshot = List.copyOf(domainEvents); domainEvents.clear(); return snapshot; }
  • •pull 而非 publish：让 domain 不依赖消息基础设施。
  • •买 5 个杯子：传统三层在 order service 直接查库存（强耦合）；DDD 发事件让库存上下文监听处理（解耦）。

    • 🗄 仓储接口：领域层说「我需要什么」

    只有接口，没有 @Repository / JPA。

    public interface OrderRepository { Order save(Order order); Optional<Order> findById(OrderId orderId); List<Order> findByCustomerId(String customerId); }
  • •返回的是聚合 Order，不是数据库 PO。
    • 八、基础设施层 · 8.1

    仓储实现：把聚合翻译成数据库行

    // infrastructure/persistence/OrderRepositoryImpl.java @Repository public class OrderRepositoryImpl implements OrderRepository { private final OrderJpaRepository jpa; // Spring Data 技术接口 public Order save(Order order) { OrderPO po = jpa.findById(order.orderId().value()) .orElseGet(() -> OrderMapper.toPO(order)); return OrderMapper.toDomain(jpa.save(po)); } }
  • •依赖倒置闭环：外层实现了内层定义的接口，内层一行不改就能换数据库。
    • 八、基础设施层 · 8.2

    聚合与 PO 是两个模型

    聚合 Order持久化对象 OrderPO
    注解 / setter无 @Entity、无 setter有 @Entity、有 setter
    业务规则有无
    目的表达业务映射数据表
  • •OrderMapper.toPO()：领域聚合 → PO（保存方向）。
  • •reconstruct：PO → 聚合（恢复方向，绕过业务校验，因为数据已合法）。
    • 九、事件落地与何时用 · 9.1

    领域事件落地：事务提交后再发

  • •消费者统一用 @TransactionalEventListener(phase = AFTER_COMMIT)：事务提交后才派发，消费者绝不会读到未提交数据。
    • 事务 A：订单支付（只改 Order）→ 提交 ──AFTER_COMMIT──► 事务 B：商品扣库存 → 提交
  • •一个事务一个聚合 → 事件达成最终一致（扣库存失败需补偿，代码里有告警日志）。
    • 九、事件落地与何时用 · 9.2

    什么时候用 DDD

    适合不适合
    业务规则复杂、持续变化、长期维护的核心域简单 CRUD、报表系统

    ⚠️ AI 生成代码默认三层架构

    你不明确告诉 AI「按 DDD 区分四层」，AI 只会生成三层架构的代码——因为全世界的代码大多是三层写法，AI 永远按最常见的方式生成。用 AI 辅助编程时，要主动、明确描述 DDD 的分层要求。

    常见误区正解
    DDD = 分层和类名核心是 边界与不变量
    所有模块都要 DDD只用在核心域
    聚合越大越好越小事务冲突越少
